WarpWarp

Warp
编程 终端 多模型 协作 云端 开源 partial lifecycle: active 核验Checked 2026-10-08

开源客户端的终端 agent 环境——官方自称「Agentic Development Environment」， 把现代终端、编码 agent、Warp Drive 协作与云 agent / Factories 合成一个产品。Warp calls itself, verbatim, an open-source Agentic Development Environment that "brings together terminal work, coding agents, and cloud automation". The same Warp Agent is reachable three ways — "In the Warp app", "In any terminal, with the Warp Agent CLI", "In the cloud, as a cloud agent" — with account, rules, skills and model access shared across all three. The CLI is "a standalone terminal program" and "a native terminal multiplexer" with its own PTY, so it runs in any terminal emulator, including over SSH. Every proposed action is checked against an execution profile whose values are agent_decides / always_ask / always_allow; file edits still prompt every time by default, so "you always review a diff before it's applied".

适合与不适合When to use it, when not to

在终端里同时做命令执行与编码 agent 工作、并希望团队协作与云自动化的用户。 把终端工作流标准化为 Workflows / Notebooks，或把 issue triage、 PR review 等后台活交给云 agent，是它的重点场景。

不适合完全不碰终端 agent、只要一个经典终端的用户—— Free 档可以当现代终端用，但云 agent、Warp Drive 协作与代码库索引都受限。

Developers who run both shell commands and coding agents in the terminal and want team collaboration plus cloud automation. Particularly good for: teams standardizing terminal workflows as Warp Drive Workflows / Notebooks; teams delegating background work such as issue triage or PR review to cloud agents; enterprises that need SSO, data governance or self-hosted cloud agents.

Not a fit for people who avoid terminal agents entirely and just want a classic terminal — the Free tier works as a modern terminal, but cloud agents, Warp Drive collaboration and codebase indexing are all capped.

模型与开放条件Model & openness
多模型 + BYOK，官方明确「pick a model per conversation」。 官方 CLI 页写「Pick a model per conversation, bring your own provider API keys, and track credit usage」；定价页 Build 档描述模型来源为 「frontier and open-source models from OpenAI, Anthropic, z.ai, and more」。 BYOK 有档位边界：官方定价表把「Bring your own API key」与 「Custom inference endpoint」标注为「Individuals and orgs up to 10 people」， 即个人与 10 人以内组织可用；Enterprise 档另有 BYOLLM （官方原文「Route inference through your own cloud (BYOLLM)」）。 换模型：CLI 侧可逐会话选模型，执行 profile 里也能设 base_model 覆盖。 官方未在定价页列全模型清单（已查 pricing 与 agents/cli 两页）。
运行位置Where it runs
CLI 优先，但同一 agent 有三种运行面。 官方文档原文「Warp is an open-source Agentic Development Environment」， 三种入口共用同一 Warp Agent：「In the Warp app」「In any terminal, with the Warp Agent CLI」「In the cloud, as a cloud agent」。 CLI 是独立终端程序——官方原文「a standalone terminal program that runs the Warp Agent」，本身是「a native terminal multiplexer」（自带 PTY）， 可在任意终端模拟器中运行，包括通过 SSH；启动命令是 warp （云侧另有 oz 命令）。账号、规则、技能与模型访问跨三种入口一致， 且官方注明 CLI 不要求安装 Warp 桌面 app。 本条目记录 CLI 形态；桌面 app 与云 agent 的差异以官方页面为准。
本地文件Local files
在本地 checkout 内工作，官方强调可评审的 diff 与索引边界。 官方 CLI 页的「Project context」写明 agent 会自动读取项目规则 （如 AGENTS.md）、skills 与 MCP 配置。文件改动以 diff 呈现， 默认 apply_code_diffs 为 agent_decides，但编辑文件仍每次提示—— 官方原文「you always review a diff before it's applied」。 目录授权：执行 profile 有 directory_allowlist，控制 「Directories the agent may read without approval」。 代码库索引按档给上限（定价页）：Free 3 个代码库 / 每库 3,000 文件， Build 与 Max 40 个 / 每库 100,000 文件，Business 80 个，Enterprise 定制。 索引算法与首次建索引耗时官方未说明（已查 pricing 与 agents/cli 两页）。
关机后的任务Tasks after shutdown
云端后台形态官方明确，属「真后台」。 终端 agent 绑定会话；但官方文档把 Automation Platform 与 cloud agents 单列——「Run background agent work in the cloud」， 可由 triggers、schedules、integrations 与 API 触发， 官方点名用途含 issue triage、pull request review、周期性维护。 Warp Factories 更进一步：一组挂在仓库上的云 agent， 从 Slack / GitHub / Linear / Jira 取活，走 triage → spec → implement → review， 产出通常是 PR。CLI 侧还有 cloud handoff——可把会话交给云 agent， 或把云 run 拉回终端继续。云 agent 的并发与算力按档给（定价页）： Free 有限、Build 20 并发 / 2 vCPU 4 GiB、Max 20 / 4 vCPU 8 GiB、 Business 80 / 8 vCPU 16 GiB、Enterprise 定制。
工具与扩展Tools & extensions
终端内 agent + MCP 支持完整（本地与云端两套）。 内置能力围绕终端：自然语言提示、agent 会话转录（流式响应、Markdown、 文件 diff、工具调用、计划与任务列表）、在同一输入里跑 shell 命令、 云 handoff 与多 agent 协调。Warp Drive 提供 Workflows / Notebooks / Prompts / 环境变量等可复用对象。 MCP（本地 agent）：官方原文支持「Streamable HTTP and SSE」， 以及 CLI（Command）本地 server；配置分项目级 .warp/.mcp.json 与 全局 ~/.warp/.mcp.json，还能读取第三方 agent 的 MCP 配置 （Claude Code、Codex 等），有内置技能 /agent-add-mcp； 认证支持环境变量、OAuth 一键安装与自定义 Header；安全上 「Project-scoped servers never auto-spawn」。 MCP（云 agent）：支持 command/args（stdio）、url （Streamable HTTP / SSE）与 warp_id（引用已授权的托管 server）， OAuth 走 managed MCP installation。
上下文与记忆Context & memory
会话持久化到账号，可退出续接与切换。 官方 CLI 页原文「Conversations save to your Warp account, so you can exit and resume later or switch between them」；交互侧 /status 可看当前会话 名与 ID。项目上下文自动注入：agent 自动读取项目规则（如 AGENTS.md）、 skills 与 MCP server。Warp Drive 里保存的 prompt 登录后可用， 但官方明确 CLI 内仅 prompt 类对象可用——「other Warp Drive object types aren't available in the CLI」。跨 agent 记忆列为 Enterprise 的 「Cross-harness agent memory (Research Preview)」。 上下文压缩策略与跨项目记忆边界官方未说明 （已查 agents/cli 与 warp-drive 两页）。
权限与限制Permissions & limits
执行 profile + 三档值 + auto-approve 的终端内审批模型。 官方原文「Every action the agent proposes ... is checked against your active execution profile」。权限值三档：agent_decides（自信则自走、 不确定才问）、always_ask、always_allow。默认下 shell 命令、 文件编辑、文件读取、MCP 工具调用均为 agent_decides； 文件编辑的 agent_decides 仍每次提示，保证「always review a diff before it's applied」。另有 command_allowlist / command_denylist （denylist 即使 always_allow 也要批准）、directory_allowlist、 write_to_pty、run_agents、ask_user_question。 Auto-approve（/auto-approve 或 Ctrl+Shift+I）给全自主， 作用域限单会话、新会话默认关闭；默认会绕过 command denylist（可关掉）， 但团队管理员在 Admin Panel 设的 denylist 永不被绕过。 执行 profile 仅存本地、不同步到云端。
适合什么任务Best for
在终端里同时做命令执行与编码 agent 工作、并希望团队协作与云自动化的用户。 特别适合：想把终端工作流标准化为 Workflows / Notebooks 的团队、 想把 issue triage / PR review 等后台活交给云 agent 的团队、 需要 SSO / 数据治理 / 自托管云 agent 的企业。 不适合：完全不碰终端 agent、只要一个经典终端的用户—— Free 档虽可当现代终端用，但云 agent、Warp Drive 协作与代码库索引都有额度上限。

头号误解Top misconception

  • 把 Free 当成能无限用 agent，官方写的是 Limited cloud agents accessAssuming Free means unlimited agent use — the official page says "Limited cloud agents access"
  • 以为 auto-approve 也绕过禁用命令，团队在 Admin Panel 设的 denylist 不会被绕过Assuming auto-approve bypasses the command denylist — a team denylist set in the Admin Panel is never bypassed
