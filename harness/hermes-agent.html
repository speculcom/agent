Hermes AgentHermes Agent

Nous Research
Python 开源 MIT 通用harness 通用助手 常驻 跨平台消息 定时任务 MCP 子代理 RPC 技能系统 记忆 上下文压缩 权限审批 自托管 partial lifecycle: active 核验Checked 2026-10-01

Hermes Agent 是一个常驻的跨平台个人助手，会从经验里自己攒技能。

它不绑在你的笔记本上。

官方 README 说：
The self-improving AI agent built by Nous Research. It's the only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, and builds a deepening model of who you are across sessions. Run it on a $5 VPS, a GPU cluster, or serverless infrastructure that costs nearly nothing when idle. It's not tied to your laptop — talk to it from Telegram while it works on a cloud VM.

⚠ 「the only agent」这句话，本站的态度是： 这是官方自我宣传语。 本站未做跨产品对比测试来验证 "only" 是否成立。 记录为官方声明，不是本站结论。

Hermes Agent is a resident cross-platform personal assistant that accumulates its own skills from experience. It is not tied to your laptop — the official README says:

The self-improving AI agent built by Nous Research. It's the only agent with a built-in learning loop — it creates skills from experience, improves them during use, nudges itself to persist knowledge, searches its own past conversations, and builds a deepening model of who you are across sessions. Run it on a $5 VPS, a GPU cluster, or serverless infrastructure that costs nearly nothing when idle. It's not tied to your laptop — talk to it from Telegram while it works on a cloud VM.

⚠ This site's position on "the only agent": that is the vendor's own marketing line. This site ran no cross-product comparison to test whether "only" holds. It is recorded as a vendor claim, not as this site's conclusion.

适合与不适合When to use it, when not to

适合这六类场景。

  • 想要常驻的跨平台个人助手
  • 放云 VM / serverless，不绑在自己的笔记本
  • 需要定时任务无人值守
  • 需要跨会话记忆与技能自积累
  • 想用自建 endpoint 或多 provider
  • 需要命令级审批 + DM 配对做安全边界

不适合这四类场景。

  • 只做编程任务
  • 需要当嵌入式 SDK
  • 需要「状态 vs 上下文」分层保证
  • 需要企业级多用户与审计

A fit for these six cases.

  • A resident cross-platform personal assistant (six platforms: Telegram / Discord / Slack / WhatsApp / Signal / Email)
  • Running it on a cloud VM or serverless, rather than tied to your laptop
  • Scheduled tasks that must run unattended
  • Cross-session memory and self-accumulating skills
  • Using your own endpoint or multiple providers such as OpenRouter
  • Command-level approval plus DM pairing as a security boundary

Not a fit for these four cases.

  • Coding tasks only — it is a general assistant; coding is one of many things
  • Using it as an embedded SDK — it is a complete runtime, not a library
  • A detailed "state vs context" layered guarantee — it has many mechanisms, but the vendor does not split them along those two layers

⚠ Unknown: enterprise multi-user and audit. The vendor provides no separate documentation.

Checked the security and messaging pages: both cover only single-owner allowlist / DM pairing authorization, not multi-tenant audit.

模型与开放条件Model & openness

官方给了四种路径，并且强调没有锁定。

这是本站收录对象里，对模型自由度表述最直白的一个。

README 原文：

"Use any model you want — Nous Portal, OpenRouter, OpenAI, your own endpoint, and many others. Switch with hermes model — no code changes, no lock-in."

「your own endpoint」这一条对本站读者最有用。 自建网关、自托管推理都能直接接。

换模型不改代码，用一条运行时命令：/model [provider:model]。 这条命令 CLI 与消息平台共用。 （见站点上的 CLI vs Messaging 对照表）

完整 provider 清单已核验，来源是官方 docs/integrations/providers。 官方一共列出 40+ 家：

  • Nous Portal —— 官方称 "300+ frontier agentic models"
  • OpenRouter、Anthropic、GitHub Copilot
  • xAI Grok、Google Gemini / Vertex AI
  • AWS Bedrock、Azure AI Foundry
  • DeepSeek、Hugging Face、NVIDIA Build
  • 本地 / 自托管：Ollama、LM Studio，以及 Custom Endpoint

Custom Endpoint 的配置官方说：

"saved in config.yaml"

官方对那一页的定位原文：

"from cloud APIs ... to self-hosted endpoints like Ollama and vLLM, to advanced routing and fallback configurations."

⚠ 未知：换模型后的能力对齐度、本地量化模型在多后端下的行为差异，官方未给结论。

本站也没有实测。

核验：已查 providers 页与 configuration 页。

运行位置Where it runs

这是它最强的一维：七种终端后端，加两个入口。

README 原文列举：

"Seven terminal backends — local, Docker, SSH, Singularity, Modal, Daytona, and Vercel Sandbox."

官方还特别点出这两个后端：Daytona 与 Modal。 它们带来 serverless persistence。

"your agent's environment hibernates when idle and wakes on demand, costing nearly nothing between sessions"

入口有两个。 README 有一张专门的 CLI vs Messaging 对照表：

  • 终端 TUI：启动 hermes
  • 消息平台：先跑 gateway，再从 Telegram / Discord / Slack / WhatsApp / Signal / Email，以及 Home Assistant 聊天

⚠ 这是本站最有价值的一格。 它是唯一明确说「agent 可以跑在云 VM 上、 你从 Telegram 指挥它」的收录对象。

这和 OpenHands 的「关掉笔记本后 agent 仍在跑」是同一类诉求。 区别是：OpenHands 把它做成可选部署项，Hermes 把它做成了默认形态。

本地文件Local files

本地文件能力是间接获得的：它靠终端后端，而不是框架自己。

隔离机制见 permissions 维度。

工作区由所选后端决定。 官方 terminal.backend 默认是 local。

官方给的标注原文："Run on your machine (default)"

terminal.backend 决定工作区。 工作目录由 cwd 决定。

这些后端各自提供一层隔离：

  • Docker / SSH
  • Singularity
  • Modal / Daytona / Vercel

Context Files 是官方的一等概念，格式与优先级已核验。 （文档 features/context-files） 支持的文件名如下：

  • .hermes.md / HERMES.md
  • AGENTS.md、AGENTS.override.md
  • CLAUDE.md
  • SOUL.md
  • .cursorrules、.cursor/rules/*.mdc

优先级是 first match wins。 顺序原文如下：

.hermes.md → AGENTS.override.md → AGENTS.md → CLAUDE.md → .cursorrules。 SOUL.md 是身份文件，始终单独加载。

在 git 仓库里，整条 AGENTS.md 链按 git root → 工作目录 合并。 会话中还会渐进发现子目录 context。 每个文件的字数上限是 floor 20,000 / ceiling 500,000。

文件访问有边界。 安全页第 8 层管的是 terminal 后端的工作目录参数：

官方原文："validated against an allowlist to prevent shell injection"

安全页第 3 层说，write_file 与 patch 有 denylist。 另有可选 write sandbox。

关机后的任务Tasks after shutdown

这一维它的机制最厚，官方给了三重机制。

① 内建 cron 调度器。 官方特性表原文：

"Built-in cron scheduler with delivery to any platform. Daily reports, nightly backups, weekly audits — all in natural language, running unattended."

（文档 features/cron）

② serverless 休眠后唤醒。 Daytona / Modal / Vercel 后端空闲时休眠、需唤醒， 官方原话是这两个词： 官方原文："hibernates when idle and wakes on demand"

③ 常驻网关进程。 gateway 一旦运行，就能从多个消息平台随时触发。

补偿与补跑机制官方已写明（features/cron）：

  • 有 misfire catch-up 扫描
  • resume 之后 "the next tick fires one catch-up run"
  • 补跑可关：cron.catch_up_missed: false
  • 全局 hermes pause 期间，托管 cron 的 fire webhook 返 503 Retry-After: 60， 让调度器重投
  • 官方称 "nothing is lost: due work catches up on the first tick"
  • 运行中的任务 "never killed"

网关侧还有 event-loop liveness watchdog。 它连续 3 次探针无响应就以 code 75 退出，由 supervisor 重启。 另有 60s 心跳。

⚠ 未知：跨休眠 / 唤醒的状态一致性，官方未说明。

核验：已查 features/cron、features/tools、user-guide/messaging 三页。

上下文与记忆Context & memory

⚠ 这一维是本站最看重的，也恰好是本对象宣传力度最大的，必须分开核实。

先看官方声明。

README 特性表 "A closed learning loop" 一行原文：

"Agent-curated memory with periodic nudges. Autonomous skill creation after complex tasks. Skills self-improve during use. FTS5 session search with LLM summarization for cross-session recall. Honcho dialectic user modeling. Compatible with the agentskills.io open standard."

但把官方给的机制逐个归位，会发现它不是一个维度，而是三个。

官方说法本站归类说明
periodic nudges（自我提示）状态面机制触发器，不是压缩算法
FTS5 session search + LLM summarization上下文面 ✅检索 + 摘要，这是真正的上下文管理
Skills（自主创建 + 使用中自我改进）独立一层程序性记忆，与对话上下文不同
Honcho dialectic user modeling独立一层对用户的长期建模

关键区分点：压缩是用户显式触发的。 它有明确的 /compress 命令， CLI 与消息平台都有，对照表里与 /usage、/insights 并列。 也就是说：不触发就不会压缩，它不是自动的。

还有一组能落到文件名的证据。 来自 "Migrating from OpenClaw" 章节， 这是少见的官方一手清单：

  • SOUL.md —— persona
  • MEMORY.md 与 USER.md —— 记忆条目
  • AGENTS.md —— 工作区指令
  • ~/.hermes/skills/openclaw-imports/ —— 技能目录

这说明记忆是明文的 markdown 文件，可读、可迁移。 对本站读者来说这是重要优点。

权限与限制Permissions & limits

官方文档里有一节独立的 "Security"，把权限面拆成了八层。

八层原文列的是：

  • user authorization（allowlists、DM pairing）
  • dangerous command approval
  • file write safety
  • container isolation
  • MCP credential filtering
  • context file scanning
  • cross-session isolation
  • input sanitization

逐项核验（官方 user-guide/security）：

① Command approval（默认值已核验）。 approvals.mode 有三档，默认 smart。

  • smart —— 用辅助 LLM 评风险；低危命令自动批准，真正危险自动拒绝， 不确定的升级为手动
  • manual —— 每次都问
  • off —— 等于 --yolo

超时默认 300 秒，未回复即 fail-closed。

另有始终生效的 hardline blocklist。它包含：

  • rm -rf /
  • fork bomb
  • dd 写块设备等

--yolo 或 approvals.mode: off 都不能越过它。

还有用户可编辑的 deny 规则：approvals.deny。 它用 fnmatch glob、大小写不敏感。 可以写成 "yolo 但除这些之外"。

② DM pairing（默认拒绝）。 授权检查按这个顺序走：

  • 平台 allow-all
  • DM pairing 已批准名单
  • 平台 allowlist（TELEGRAM_ALLOWED_USERS 等）
  • 全局 allowlist
  • 全局 allow-all
  • Default: deny

配对流程是 8 位码：

hermes pairing approve <platform> <code> unauthorized_dm_behavior 默认 pair。 另可设 ignore / decline。 配对码 1 小时过期、限速，5 次失败锁 1 小时。

③ Container isolation（默认关）。 terminal.backend 默认 local。 容器隔离只在改用特定后端时才启用：

  • docker / ssh / singularity
  • modal / daytona / vercel

启用后，官方列出一整套 Docker 加固 flag：

  • --cap-drop ALL
  • --security-opt no-new-privileges
  • --pids-limit 256
  • noexec tmpfs 等

迁移脚本会碰密钥。 hermes claw migrate 会导入五家 API keys：

  • Telegram
  • OpenRouter / OpenAI
  • Anthropic
  • ElevenLabs

官方给了 --dry-run 预览。

⚠ 未知：gateway 端口安全，官方未单列一节。

dashboard 侧有 OAuth / 自托管 OIDC 鉴权。

适合这六类场景。

  • 想要一个常驻的跨平台个人助手 （六个平台：Telegram / Discord / Slack / WhatsApp / Signal / Email）
  • 想把它放在云 VM 或 serverless 上，不绑在自己的笔记本

头号误解Top misconception

  • 当成编程框架用 —— 它是通用个人助手，编程只是它能做的事之一，形态与 LangGraph/CrewAI 完全不同Using it as a programming framework — it is a general personal assistant; coding is one of many things it does, and its form is nothing like LangGraph/CrewAI
  • 相信「the only agent with a built-in learning loop」是本站结论—— 那是官方宣传语，本站未做跨产品对比验证Taking "the only agent with a built-in learning loop" as this site's conclusion — that is the vendor's marketing line; this site ran no cross-product comparison
  • 把七种终端后端理解成七种部署方式 —— 官方说的是 terminal backends（工具执行的后端），且其中 Modal/Daytona 提供的是休眠不是常驻Reading the seven terminal backends as seven deployment modes — the official text says terminal backends (the backend that executes tools), and Modal/Daytona there provide sleep, not always-on
  • 以为 /compress 是自动的 —— 它是显式命令，不触发就不会压缩Assuming /compress is automatic — it is an explicit command; nothing is compressed unless you trigger it
  • 忽略 DM pairing 的重要性 —— 一个能接六个消息平台、还能在文件系统动手的 agent，谁能指挥它就是最关键的安全问题Overlooking DM pairing — for an agent that reaches six messaging platforms and touches your filesystem, who can command it is the central safety question
  • 跑 hermes claw migrate 前不看 dry-run —— 该命令会接触 API keys（README 列出五家）Running hermes claw migrate without reading the dry-run first — the command touches API keys (the README lists five providers)
  • 不确认就迁移 —— Hermes 与 OpenClaw 的关系本站未核验，只记录 README 的一手事实Migrating without confirming — this site's view of the Hermes / OpenClaw relationship was not verified; it records only the README's first-hand facts

七种终端后端：这是它最独特的一格

README 原文：
Seven terminal backends — local, Docker, SSH, Singularity, Modal, Daytona, and Vercel Sandbox. Daytona and Modal offer serverless persistence — your agent's environment hibernates when idle and wakes on demand, costing nearly nothing between sessions.

⚠ 两点要说清。

① 这是 terminal backend，指的是「工具在哪执行」，不是七种部署方式。 local 就是本机执行，Docker/Singularity 是容器，SSH 是远端机， Modal/Daytona/Vercel 是 serverless。

② 「空闲时休眠」不等于「常驻」。 官方用词是 hibernate，唤醒有延迟。 休眠期间的状态一致性本站未核验。

对比 OpenHands：它也主打「关掉笔记本后 agent 仍在跑」。 区别是那是可选的部署形态，而 Hermes 把它做成了默认形态。

记忆与上下文：机制最多，但官方没按本站关心的两层分

Agent-curated memory with periodic nudges. Autonomous skill creation after complex tasks. Skills self-improve during use. FTS5 session search with LLM summarization for cross-session recall. Honcho dialectic user modeling. Compatible with the agentskills.io open standard.

把官方给的机制逐个归位，会发现这是三个不同维度混在一句话里：

官方说法本站归类说明

权限：六个平台入口让「谁能指挥它」成为核心问题

README 的文档目录里有一节独立的 Security，副标题原文：

Command approval, DM pairing, container isolation

逐项解读。

① Command approval —— 命令级审批。 默认 smart：辅助 LLM 评风险，低危自动批准、危险自动拒绝、不确定转手动。 超时 300 秒 fail-closed。 另有始终生效的 hardline blocklist，它不受这两个开关影响。

用户还能自己写 deny 规则：approvals.deny。 它用 fnmatch glob、大小写不敏感。

这与别家的做法不在同一层。

  • OpenHands 用 API key 机制
  • Codex SDK 有四种 ApprovalMode

② DM pairing —— 私聊配对，即只有配对过的用户能指挥它。 默认拒绝：授权检查顺序里，pairing 已批准名单排在平台 allowlist 之前。 全未命中即 deny。 配对流程是 8 位码：

  • hermes pairing approve <platform> <code>
这一项在六个消息平台入口的前提下极其重要。 一个能通过 Telegram / WhatsApp 接指令、还会在文件系统上动手的 agent， 「谁能给它下指令」就是最关键的安全问题 —— 这也是本站把它单独列出来的理由。

③ Container isolation —— 容器隔离。默认关。 terminal.backend 默认是 local。 改用下面这组后端时才会启用隔离：

  • docker / ssh
  • singularity
  • modal / daytona / vercel
