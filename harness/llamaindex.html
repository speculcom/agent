适合与不适合When to use it, when not to

适合：核心任务是把外部数据源接进来做检索与问答；需要 300+ 集成里的某一个。 不适合：主要目的是多 Agent 编排 / 工作流（那部分在商业平台 LlamaAgents）； 需要 agent 在工作区读写文件（那是 Deep Agents 那一类）；需要明确沙箱与权限边界。

Fits: the core task is bringing external data sources in for retrieval and question answering; needing one of the 300+ integrations. Not a fit: multi-agent orchestration / workflow as the main goal (that part lives in the commercial LlamaAgents platform); agents that read and write files in the workspace (that's the Deep Agents category); explicit sandbox and permission boundaries; a context-compaction mechanism for long tasks.

模型与开放条件Model & openness
形态是「300+ 分散的集成包」，不是统一网关；官方称其为社区集成。 README 原文："There are over 300 LlamaIndex integration packages that work seamlessly with core, allowing you to build with your preferred LLM, embedding, and vector store providers." 命名空间约定：from llama_index.core.xxx 是核心， from llama_index.xxx.yyy 是集成包（带 .core 用核心，不带用集成）。 官方 integrations 页把这些包归为 "community integrations"（社区集成）， README 说新集成需经维护者审核（"some integrations may be declined"）。 官方未公布集成包的质量分层与维护活跃度分级（已查 README 与 integrations 页）。
运行位置Where it runs
OSS 形态是纯库，且有两个安装档位；托管运行在商业平台侧。 ① Starter：llama-index（PyPI）—— 核心 + 一批常用集成的合集； ② Customized：llama-index-core —— 只装核心，再按需从集成页挑包。 框架本身是被 import 的库，集成方式是与外部应用框架对接 （README Proposed Solution 第四条 "integrations with your outer application framework"）。 官方另有一套托管/部署路径：LlamaAgents 的 llamactl CLI 可 "serve locally, and deploy to LlamaCloud or export for self-hosting"，LlamaCloud 另有托管 Index。 即托管是 LlamaCloud / LlamaAgents 那一层（商业），不是 OSS 自带的运行形态。
本地文件Local files
它不是「agent 工作区」文件系统，而是「数据源接入 + 索引」层的本地文件读取。 官方 SimpleDirectoryReader 文档原文："the simplest way to load data from local files into LlamaIndex"，可传 input_dir、recursive=True、exclude、 required_exts、num_files_limit，并支持 fsspec 远程文件系统（S3、GDrive 等）。 索引默认存内存，官方示例可 index.storage_context.persist() 落到 ./storage 再 load_index_from_storage 重载。 本站按「索引层视角」记这一轴：它读盘是为了把文档变成可检索的索引， 与 Deep Agents 那种「agent 在工作区里改文件」不是一回事。
关机后的任务Tasks after shutdown
OSS 是库，没有「关机后继续跑」的托管执行；但编排（Workflows）仍留在 OSS。 先纠正一个易被 README 误导的点：README 把 Workflows 列在 LlamaParse 平台的 Agents 节，但官方框架文档明示 Workflows 仍在开源核心里 —— "llama-index-core comes with a stable version of Workflows included"， import 路径为 llama_index.core.workflow，也可独立 pip install llama-index-workflows。 即编排并未被移出 OSS。 至于后台执行：官方框架文档未提供「关机续跑」的托管运行时， 进程要你自己跑；需要托管时走 LlamaAgents / llamactl 部署到 LlamaCloud 或自托管 （原文 "deploy them to LlamaCloud or your own infrastructure"），那是平台侧。
工具与扩展Tools & extensions
工具层两件事：社区 ToolSpec + 官方 MCP 接入包。 官方 tools 文档给出 FunctionTool / QueryEngineTool 与 "Community contributed ToolSpecs"，并有 Utility Tools 处理「工具返回超大输出」 （OnDemandLoaderTool / LoadAndSearchToolSpec）。 MCP：官方支持，且是独立包 —— 文档原文 "LlamaIndex provides robust support for consuming MCP servers through the llama-index-tools-mcp package"， 支持 SSE / Streamable HTTP / stdio 三种传输，还能把 Workflow 反发布为 MCP server； 官方另托管 mcp.llamaindex.ai（文档检索 / LlamaParse 的 MCP 服务）。
上下文与记忆Context & memory
这一维度官方有具体机制，不是空白。 README 对框架的定位是 "data framework"，核心能力是 structure your data （indices, graphs）+ retrieval/query interface —— 即处理「把外部数据变成可检索的上下文」。 检索后如何塞进上下文窗口，官方用 Response Synthesizer 回答（原文）： compact（默认）"stuff as many text ... that can fit within the context window"、 refine（逐块精炼）、tree_summarize（递归摘要）、simple_summarize（截断到单 prompt）。 这就是它的上下文裁剪与摘要机制：先按窗口装箱，装不下再切块，摘要类模式做压缩。
权限与限制Permissions & limits
⚠ 本站明确的重大信息缺口，选型前必须自己确认。 README 全文没有任何沙箱、文件权限模型、网络访问控制或人工确认机制的表述。 与本站收录的其它编排框架对照： Google ADK 有 Tool Confirmation（HITL）、CrewAI 有 guardrails（机制未说明）、 LangGraph 有 interrupts（可检查并修改状态）—— LlamaIndex 在这一维度上 README 里连一个名词都没有。 ⚠ 需特别注意：由于它的主战场是文档解析与 RAG， 它处理的通常是用户上传的数据，这本身是一个与「agent 动你本地文件」性质不同的风险面， 但 README 未讨论数据权限与隔离。
适合什么任务Best for
适合：核心任务是把外部数据源（API / PDF / 文档 / SQL）接进来做检索与问答， 需要 300+ 现成集成里的某一个；团队 Python 栈； 或明确要用 LlamaParse 的解析能力（那走商业平台）。 不太适合：需要 agent 在自己项目目录里读写文件并跑命令 （那是 Deep Agents 那一类「工作区文件系统」）；需要明确的沙箱与权限边界 （官方框架文档无此类机制）；需要「关机后托管续跑」（走 LlamaAgents 平台侧）。
