LangGraph 是一个低层编排框架，专门用来构建有状态的 agent。

官方自述很克制，注意那个 low-level：

Low-level orchestration framework for building stateful agents.

它自认不是开箱即用的高层封装。 它打的是「长时间运行、有状态」这件事的地基。

LangGraph is a low-level orchestration framework for building stateful agents.

The official description is deliberately modest — note that word, low-level:

Low-level orchestration framework for building stateful agents.

It does not claim to be a batteries-included high-level wrapper. It lays the groundwork for long-running, stateful work.

适合与不适合When to use it, when not to

适合：agent 流程要跑很久且必须能从中断处精确恢复；要人工在流程中间介入并改状态； 要分开管理工作记忆与跨会话记忆；需要显式图结构（分支、循环、子图）。

不适合：需要内建沙箱或文件级权限边界（官方未提供此类机制，2026-10-08 核验）； 想要开箱即用的文件系统与子代理（走 Deep Agents）；不想额外依赖 LangChain 生态。

Fits: agent flows that run long and must resume precisely from an interruption; a human stepping into the middle of a flow to change state; managing working memory and cross-session memory separately; an explicit graph structure (branches, loops, subgraphs); teams on Python. Not a fit: needing built-in sandboxing or file-level permission boundaries (official docs do not provide such a mechanism — checked the README and the interrupts page); wanting a filesystem and sub-agents out of the box (go with Deep Agents, the higher-level package built on LangGraph); not wanting an extra dependency on the LangChain ecosystem — model access usually goes through it.

模型与开放条件Model & openness

LangGraph 完全不碰模型 —— 这是它作为低层框架的设计取向。

官方自述的五项能力是 durable execution / HITL / memory / LangSmith 调试 / 生产部署。 这五项全部与模型无关，没有一处列出 provider。 官方 overview 把「models」归到 LangChain 那侧：

官方原文："starting with models and tools"

官方 overview 还写明：

官方原文："LangGraph does not abstract prompts or architecture."

接模型通常经 LangChain 集成层（init_chat_model 或任一 SDK）。 但官方明说它

官方原文："can be used without LangChain"

这句在官方首页文末，不是强绑定。

官方未提供任何 provider 清单 —— 模型本就不在其职责内。 overview 与官方首页两处都没有列。

⚠ 本站判断：它不绑模型，官方首页也没有 provider 清单。

运行位置Where it runs

OSS 形态是纯库，没有运行时服务。

安装就是 pip install -U langgraph。 没有 CLI 启服务、没有容器编排、没有 Web UI（Web UI 在 Deep Agents / LangSmith 那侧）。

生产部署官方指向 LangSmith Deployment。 官方 overview 把「Production-ready deployment」链到 LangSmith Deployment。 该页对它的定义是：

官方原文："a workflow orchestration runtime purpose-built for agent workloads"

它配 langgraph deploy。 环境分四档：Cloud / Hybrid / 自托管 K8s / Standalone Agent Server。 Cloud 需 Plus 档及以上。

即托管运行落在商业平台那一层；OSS 本身只负责「你自己把进程跑起来」。

本地文件Local files

⚠ 文件系统不在 LangGraph 的职责范围内。

官方首页讲文件系统的唯一位置，是把 Deep Agents 作为高层包推荐：

官方原文："leverage file systems for complex tasks"

即文件能力被归到上层封装，而不是底层图引擎。

LangGraph 本身给的是状态容器 —— checkpoint 里存的是 graph state。 至于 agent 要不要读写磁盘、用什么工具读写，不归它管。

本站判断（推断）：想要文件系统，得自己接工具，或走 Deep Agents 那一层。

关机后的任务Tasks after shutdown

这是它最强的一维，且有官方明文。

第一条特性 Durable execution 官方原文是：

Build agents that persist through failures and can run for extended periods, automatically resuming from exactly where they left off.

配套是独立子包 langgraph-checkpoint。 查 libs/checkpoint，该子包首页第一段就是：

Checkpointers provide a persistence layer for LangGraph: they save graph state at every superstep, enabling human-in-the-loop, memory between interactions, durable execution, and more.

落盘粒度就是 superstep（图的一个步进）——

不是「会话结束时」，也不是「每轮对话后」

落盘后端官方给三档（persistence 页）：

  • InMemorySaver —— 存 RAM，原文说它 "does not persist between restarts"
  • SqliteSaver —— 本地文件，开发用
  • PostgresSaver —— 生产，原文 "In production, use a checkpointer backed by a database"

另有 langgraph-checkpoint-* 的 MongoDB / Redis / Oracle 实现。

跨进程恢复靠数据库 + 同一 thread_id。 官方 durable-execution 页说可以 官方原文："resume workflows from the last successful checkpoint"

langgraph>=1.2 还给了 SIGTERM 的 graceful shutdown （drain 后存下可续跑的 checkpoint）。

未知：多进程并发写同一 thread 的冲突语义官方未说明。 ⚠ persistence 与 checkpointers 两页都没有写这一点。

工具与扩展Tools & extensions

LangGraph 核心不含工具系统，但官方生态有统一 MCP 接入包。

官方自述的五项能力里没有一项是工具系统。 工具接入经 LangChain 生态，或你自己的函数 —— LangGraph 负责图与状态，工具由 LangChain 或你的函数提供。

MCP：官方提供 langchain-mcp-adapters（langchain-ai 组织）。 官方首页对它的说法是

官方原文："makes MCP tools compatible with LangChain and LangGraph"

以及 官方原文："Convert MCP tools into LangChain tools that can be used with LangGraph agents"

可连接多个 MCP server —— 这就是 LangChain 生态的统一 MCP 接入层。

注意它是独立包（pip install langchain-mcp-adapters），不在 langgraph 核心里。

上下文与记忆Context & memory

LangGraph 把「状态」和「记忆」分成两套机制，两套都有官方原文。

第三条特性 Comprehensive memory 官方原文是：

Create truly stateful agents with both short-term working memory for ongoing reasoning and long-term persistent memory across sessions.

短期记忆：官方 add-memory 页给了三条裁剪手段 —— Trim messages / Delete messages / Summarize messages。 这三条就是短上下文的管法：裁剪、删除、摘要。 该页对它们的定位是：

官方原文："techniques to manually remove or forget stale information"

长期记忆：用 store 存 JSON 文档。 官方称它支持语义搜索与内容过滤：

官方原文："supports both semantic search and filtering by content"

它可跨 thread 召回。

未知：「大工具输出落盘」官方未说明 LangGraph 提供。 ⚠ memory 与 add-memory 两页都没有 —— 那是上层 Deep Agents 的 context management 能力。

权限与限制Permissions & limits

官方给的是 human-in-the-loop，且是「检查并修改状态」级别，不只是确认。

第二条特性 Human-in-the-loop 官方原文是：

Seamlessly incorporate human oversight by inspecting and modifying agent state at any point during execution.

文档在 langgraph/interrupts。

与其它对象对比，这一点有实质差别。 三者的介入层次递进，用行内列举是因为本解析器不支持嵌套块内的列表写法：

  • OpenAI Agents SDK 的 guardrail 是校验内容（输入/输出合不合规）
  • Google ADK 的 Tool Confirmation 是拦执行（这个工具要不要跑）
  • LangGraph 的 interrupts 是改状态（在任意执行点检查并修改图的状态）

⚠ 但要说清：它明确给的不是沙箱或权限边界。 官方文档未提及文件系统权限模型、网络访问控制、工具级白名单。 与本站收录的 OpenHands（明确的 Docker 沙箱 + API key 机制）、 Codex SDK（源码里三档 SandboxMode 枚举）形成对照， LangGraph 在这一维度上目前查不到官方机制。

适合什么任务Best for

适合四类场景。

  • agent 流程要跑很久，且必须能从中断处精确恢复
  • 需要人工在流程中间介入并修改状态
  • 要把「工作记忆」与「跨会话长期记忆」分开管理
  • 需要显式图结构（分支、循环、子图）；团队用 Python

不适合三类场景。

  • 需要内建沙箱或文件级权限边界 —— 官方未提供此类机制（已查 README 与 interrupts 页）
  • 想要开箱即用的文件系统与子代理 —— 走 Deep Agents，它是 LangGraph 上的高层包
  • 不想额外依赖 LangChain 生态 —— 模型接入通常要经它

头号误解Top misconception

  • 把 Deep Agents 与 LangGraph 当两个竞品 —— Deep Agents 是建在 LangGraph 上的高层包（README 明确）
  • 用 releases/latest 判版本 —— monorepo 的 latest 不可靠：本条实测 latest 返回
  • cli==0.4.32.dev0（子包 dev 版），主包版本需从 release 列表里挑（本次核验主包为 1.2.12）
  • 把 checkpoint 持久化读成「上下文管理」—— checkpoint 存的是 graph state，
  • 上下文压缩与记忆是 README 里另设的 memory 那一层
  • 以为它自带文件系统或工具系统 —— 这两样它都不管，要么自己接，要么走 Deep Agents
  • 以为 interrupts 是权限护栏 —— 它是「检查并修改状态」，不划文件/网络边界
  • 以为装完 LangGraph 就够了 —— 官方首屏就引导用 LangSmith 做调试与部署，那是商业产品

Durable execution：落盘粒度是 superstep

第一条特性叫 Durable execution：

Build agents that persist through failures and can run for extended periods, automatically resuming from exactly where they left off.

「exactly where they left off」是关键。 不是从头重跑，是从中断的那个步进继续。

落盘机制在独立子包 langgraph-checkpoint。 查 libs/checkpoint，该子包首页第一段就是：

Checkpointers provide a persistence layer for LangGraph: they save graph state at every superstep, enabling human-in-the-loop, memory between interactions, durable execution, and more.

⚠ 这是本站见过对「状态持久化」最明确的官方定义。 粒度是 superstep（图的一个步进），不是「会话结束时」，也不是「每轮对话后」。 本站对这条粒度的记录：落盘粒度是 superstep（图的一个步进），不是「会话结束时」也不是「每轮对话后」。

⚠ 但要诚实：跨机器 / 多进程并发写同一 thread 的冲突语义官方未说明。 persistence 文档只给数据库后端与 durability 模式（2026-10-08 核验）。

状态与记忆：它分成两套机制

第三条特性叫 Comprehensive memory：

Create truly stateful agents with both short-term working memory for ongoing reasoning and long-term persistent memory across sessions.

两个时间尺度的区分，正是本站主张的同构表达：

  • checkpoint → 存流程状态（状态面）
  • memory → 另设一层，分工作记忆与跨会话长期记忆（记忆面）

⚠ 本站最想强调的一条：别把 checkpoint 持久化读成「上下文管理」。 checkpoint 存的是 graph state。 长上下文怎么裁剪，是 memory 那一层的事。 两者在本页被严格分开记录 —— 这也是 v3 铁律「状态 ≠ 上下文」的落地方式。

⚠ 本站未核验三项：

  • 短期记忆具体如何裁剪上下文（是否即压缩/摘要）
  • 长期记忆的存储后端与检索方式
  • 本站关心的「大工具输出落盘」是否属其能力

HITL 的层次不一样：它能改状态，不只是拦一下
