JulesJules

Google
编程 编码agent 云端 厂商云 常驻 审批 订阅制 免费档 并行 partial lifecycle: active 核验Checked 2026-10-08

本机什么都不装，任务跑在 Google 的云 VM 里、以 PR 的形式异步交付——官方 GA 发布页原文写它「clones your codebase into a secure Google Cloud virtual machine (VM)」并「operates asynchronously」。与本分区 IDE / CLI 形态的根本差别不是功能多少，而是交互不是实时的：你提交任务、批准计划，然后走开，回头收 PR。Google's asynchronous coding agent: point it at a GitHub repo, and it clones the code into a fresh cloud VM, plans the change, and opens a pull request for review. The difference from the IDE/CLI agents on this site is that the interaction is not live — you approve the plan and walk away. The official REST docs make the default explicit: "By default, sessions created through the API will have their plans automatically approved. If you want to create a session that requires explicit plan approval, set the requirePlanApproval field to true"; and "The automationMode field is optional. By default, no PR will be automatically created." Tiers are bundled, not sold separately: the GA post describes a free "Introductory access to Jules," "Jules in Google AI Pro: 5x higher limits" and "Jules in Google AI Ultra: 20x higher limits," noting that "Specific usage limits are listed at jules.google."

适合与不适合When to use it, when not to

适合自包含、可验证的活：修一个明确 bug、升级依赖、补测试、迁移代码片段、小范围新功能。官方对交付形态的描述是「test verified patches」与「Open PRs with runnable code and test results」——它的产出是 PR，不是给你一个可交互的会话。

不适合需要实时 shell、边跑边改的高频交互（那是 CLI / IDE 形态的强项）；也不适合需求模糊、需要大量澄清的架构级任务——官方 FAQ 自己把「vague prompts」列进任务失败的常见原因。

Self-contained, verifiable work: fixing a named bug, bumping dependencies, adding tests, migrating code snippets, small features — officially delivered as "test verified patches" and "PRs with runnable code and test results," which is exactly what makes it good for "submit the task and come back to a PR."

Not a fit for work that needs a live shell you can steer while it runs (CLI/IDE agents do that better), or vague, architecture-level tasks that need heavy clarification — the official FAQ itself lists "vague prompts" among the common causes of a failed task.

模型与开放条件Model & openness
模型由厂商指定，没有模型选择入口。 官方 GA 发布页原文 「Jules now uses the advanced thinking capabilities of Gemini 2.5 Pro」—— 这是官方可读页唯一点名到具体模型的表述；Google One 官方套餐页在 Ultra 档写 Jules「access to latest models」，即更高档位可用更新的模型。 当前默认模型与各档位的模型映射，官方可读页未单列——官方未说明 （已查 developers.google.com/jules/api 与 Google One AI 套餐页）。 这与本分区 IDE / CLI 形态形成对照：那两类常有 /model 之类的选择面， 厂商云形态把「选模型」这件事整体交给了厂商。
运行位置Where it runs
形态的答案就是本产品：任务跑在 Google 云虚拟机上，本机不装任何东西。 官方 FAQ 原文「Each task runs in a fresh virtual machine where Jules clones your repo, installs dependencies, and makes changes based on your prompt」—— 即每个任务一台全新的云 VM，并在其中 clone 仓库、装依赖。 官方 GA 发布页把这条列为卖点「Tasks run inside a cloud VM, enabling concurrent execution」。除网页（jules.google）外，还有两个客户端入口：Jules REST API （jules.googleapis.com/v1alpha）与 Jules Tools CLI；执行面始终在厂商云， 客户端只负责下达与查看。
本地文件Local files
默认与本机完全隔离：Jules 只在云 VM 里克隆仓库工作，不读写你本机的文件。 官方 FAQ 明确该 VM「executed in a secure, cloud-based virtual machine (VM) with internet access」，并要用户「treat the environment with the same security precautions you would for any public or shared compute surface」——云 VM 有 联网能力，这是能力也是风险面。官方同时警告不要把密钥、token 之类提交进仓库。 哪些仓库对 Jules 可见，由 Jules GitHub app 的授权范围决定（FAQ 指引到 GitHub 的 applications 设置里逐项调整）。
关机后的任务Tasks after shutdown
这是本形态最强的一维，官方全程按「异步」定义它。 官方原文「Jules operates asynchronously, allowing you to focus on other tasks while it works in the background」；FAQ 进一步写「You can leave the app after submitting a task」，只需打开通知。任务失败会自动重试 （官方 FAQ「Jules will retry automatically」）。 2025-12-10 官方更新再补两项主动能力：Suggested Tasks（在最多五个仓库上主动 扫描代码、提出改进，先支持 #todos）与 Scheduled Tasks（按你设定的节奏 自动执行，如依赖检查、每周例行）——官方原文「Scheduled Tasks ... you can now define the cadence and Jules will perform the task at that time」。 并发任务数随订阅档位变化（具体数字见 pricing.note）。
工具与扩展Tools & extensions
工具面集中在云 VM 内的执行能力 + GitHub 集成。 官方 FAQ 与 GA 页确认：在 VM 里装依赖、跑测试、按 setup 脚本构建； 支持语言为 JavaScript/TypeScript、Python、Go、Java、Rust（官方称 「language agnostic but works best with」，取决于 VM 里装了什么）。 不支持长驻进程——官方 FAQ 原文「Long-running processes like dev servers or watch scripts aren't currently supported in setup scripts」，npm run dev 之类跑不起来。另有前端验证能力（在 VM 内跑脚本、回传截图，见官方发布页的 web-app 测试说明）。Jules 是否支持接入 MCP server：官方未说明 （已查 developers.google.com/jules/api 与官方 FAQ 页）。
上下文与记忆Context & memory
以 Session / Activity 为上下文单位。 官方 REST 文档原文： 「Session — A continuous unit of work within a specific context, similar to a chat session. A session is initiated with a prompt and a source」， 「Activity — A single unit of work within a Session」，且一个 Session 含用户与 agent 双方的多条 activity（生成计划、发消息、更新进度）。 也就是说面向程序化调用时，上下文是「会话 + 活动」这条可轮询的状态流， 而不是一次性的对话。跨任务层面，官方提供环境快照复用（GA 页写 「reusing previous setups so new tasks run faster」）。 上下文窗口大小与长期记忆的具体实现，官方可读页未给数字——官方未说明 （已查 Jules API 页与官方 FAQ 页）。
权限与限制Permissions & limits
审批的核心是「计划审批」，且 API 与网页默认值不同。 官方 REST 文档原文「By default, sessions created through the API will have their plans automatically approved. If you want to create a session that requires explicit plan approval, set the requirePlanApproval field to true」；网页端则默认「Prompt a task and approve Jules' plan」—— 即程序化入口默认跳过人工审批，需显式打开。 代码落地方式由创建 session 时的 automationMode 决定： 「The automationMode field is optional. By default, no PR will be automatically created」，设 AUTO_CREATE_PR 才会自动开 PR。 仓库访问走 Jules GitHub app 的授权范围。隐私口径：官方 FAQ 明确 「Jules does not train on private repository content」。 额度与计费边界：免费层与 Pro / Ultra 的具体任务数官方可读页未列（见 pricing.note）， 但「额度按任务计、不按 token 计」这一点从官方 API 概念（session 即任务单位）可读出。
适合什么任务Best for
官方给自己划的活是具体的：把任务描述交进 GitHub 仓库后，它「fix bugs, update dependencies, migrate code, and add new features」，并以「test verified patches」 「Open PRs with runnable code and test results」的方式交付。 因此适合自包含、可验证的活：修一个明确的 bug、升依赖版本、补测试、 迁移代码片段、小范围新功能。 不适合：需要实时 shell、边跑边改的高频交互（本分区 CLI / IDE 形态更合适）； 需求模糊、需要大量澄清的架构级任务——官方 FAQ 自己把「vague prompts」列为 任务失败的常见原因之一。
